# The operator's seat as the machine's driver — implementation plan (2026-09-06)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox syntax. The seat driver reads the `### KEY (kind, size) — title` sections below; every section carries `dependsOn`, `touches`, `acceptance`, `commit subject`. A seat sees only `## Global Constraints`, `## Assumptions` and its own section (`tools/factory/seat/factory-brief`), so every section is written to stand alone.

**Goal:** the operator talks to a `drive` seat on core; it dispatches the machine's work through the existing driver scripts and climbs a declared ladder of models and efforts only when a rung fails, carrying the failed attempt forward. The ladder is rows in `docs/ledger/routing.toml` (SD1); the technical class is derived from `touches` (SD2); the rung follows rule A1 and a `claude` rung is a printed launch line, never a run (SD3); a fix round's brief carries the prior attempt's result, findings and diffstat (SD4); the seat unit can act — git, nix, `seat-submit`, a writable cache, no path to systemd's control socket (SD5); a root-owned spool is the one host-side actor that starts units (SD6); `drive` is a job mode on the existing unit (SD7); the seat's hook guard runs the house guard's rules (SD8); `evidence report ladder` answers the operator's sentence per model per class at n ≥ 5 (SD9); the README and the evidence runbook say how (SD10); the `driving` skill names the four verbs as commands (SD11, in the harness repo).

**Spec:** `docs/superpowers/specs/2026-09-06-operator-seat-driver-design.md` (a53d2e5; 2,289 words, M). **Decisions that bind:** `docs/decisions/2026-09-05-telemetry-store-decisions.md` (answer 3: automatic relaunch for exactly three failure classes), `2026-09-05-dsh-harness-factory-parked.md` (point 3: Anthropic-via-OpenRouter not yet; the harness routes through the table), `2026-09-03-openrouter-lane-permitted-transcripts.md` (addendum 2026-09-05 point 1: nothing automated changes the operator's saved selection), `2026-09-04-parallel-agent-workflows.md` (deterministic first, isolation second, judgement last), `2026-09-03-test-based-reality-amendments.md` (falsifiable, not merely tested; unmeasured is debt; proxies declared), `2026-09-05-planning-agent-decisions.md` (the panel; rule A1).

**Judgement calls** (each with the reason and the alternative; the section repeats it): (1) `factory_route` exits **4**, not the spec's 3, on "ladder exhausted": exit 3 is already every table fault (`factory_route … return 3` on a malformed row or a missing default, Assumption 4), and `factory-task` must tell exhaustion (escalate) from a fault (warn and use the built-in default) without parsing stderr; the alternative — one code for both — makes the climb depend on a message string. (2) The one-variable-per-step rule is kept and the spec's own first rows are made to obey it: the table lists `implement/docs/any: Flash off → Pro medium` and `review: Pro medium → opus high`, each changing model and effort at once, which the spec's `route.py check` would refuse; the docs and XS ladders climb `Flash off → Pro off → Pro medium` (three openrouter rungs, no `claude` rung — the table's "—"), and a `claude` rung is not a row in an openrouter ladder at all: it is the `claude` route's own match for the same key, reached when the openrouter ladder is exhausted, and cross-route steps are outside the one-variable check because the report never compares them (the `claude` route leaves no `.result`). The alternative — dropping the rule — loses "every climb is a measured comparison". (3) The ladder key includes the route, as the spec says ("Rows with the same route × role × kind × size × class"); the rung-N row is the one with the same key as the rung-1 winner, so a rung above 1 on a key no rung-1 lookup can win is refused by `check` as unreachable. (4) The seat's guard runs the orchestrator guard itself rather than a second engine reading a data file: `tools/orchestrator-guard.sh` already accepts dsh's lowercase tool names (`Bash | bash)`, `Edit | edit | Write | write | MultiEdit | multiedit)` — Assumption 12), dsh's `edit`/`write`/`bash` payloads carry `file_path`/`old_string`/`new_string`/`content`/`command` (Assumption 13), and its 1,300 lines took eight gate rounds (CR2 → CR2r3b); a python port would be judged row by row against it. (5) §6's record is built over what exists — the `.result` files (`tasks.read_results`) and the review files (`tasks.read_reviews`) — the way `evidence report plans` was (its docstring: "When telemetry T10a/T10b land, the rubric join moves onto their reader layer; these output lines stay"); the `tasks` stream row shape (rung, class, prior, escalate) is the telemetry sub-project's T2 (its spec is in the planning agent now — Assumption 22) and is listed under "Not in this plan" with the seam. (6) The spec's Design 1 needs what the unit lacks: dsh's bash tool spawns `bash` by name, the driver scripts run `git`, `nix develop` and `nix build`, and the seat unit's PATH carries none of them (Assumption 15); SD5 adds the lane's own idiom (`path = [ "/run/current-system/sw" … ]`, `nixosModules/modelLane.nix`) and a writable cache root, and hides the two control sockets — a prerequisite the spec implies ("each a call to the existing driver scripts"), not a widening (the binaries were readable by absolute path already). (7) `seat-submit --no-start` writes the spool marker; inside a seat unit (`SEAT_JOB_ID` set) `factory-task` submits with `--no-start --wait`; on the host the started path is unchanged. (8) The rung is derived from the key's chain suffix (rule A1: root → 1, `b`/`c` → 2, an `r` suffix → 3); `--rung N` exists for a measurement, records `rung: N (explicit)`, and is never the default. (9) The `.result`'s `route:` line keeps its shape (the telemetry T2 pattern `^(explicit|unknown|implement/(code|docs)/(XS|S|M|L))$`); `class:`, `rung:`, `prior:`, `fallback:` are separate lines.
