# The fleet — the declared list, the deploy keys, and the forge

`hosts/fleet.json` is the one declared list every host derives from: the
`deployKeys` (the FIDO2-backed SSH keys that may log in and switch a
machine as the `deploy` user), the `machines` (each machine's role — and
for a deploy-accepting machine its address, prefix, interface, host key,
firmware kind and stateVersion), the `lan` (subnet, gateway, nameservers)
and the optional `mirror` block. The module (`nixosModules/fleet.nix`) and
the tool (`tools/fleet`) both read this one file and nothing else: every
host key and address is pinned by the declaration, never accepted on first
use. In the commands below, `<a.b.c.d>` is the forge's LAN address (the
one the console's `fleet-join` prints), `<owner>/<repo>` the repository's
owner and name, `<serial>` the YubiKey's serial, `<you>` your username.

The tool's subcommands (`nix develop -c tools/fleet --help`): `keys`,
`join-script`, `enroll`, `deploy`. Yours to run, top to bottom:

## The deploy keys

1. A FIDO2 PIN must be set on each YubiKey (question 1 = `pin`). Insert a
   key and run `ykman fido info` (the line reads `PIN: … set`); if it
   reads `not set`, set one with `ykman fido access change-pin`. Do this
   on both keys.
2. Make one deploy key per YubiKey — key A first, then key B:

   ```
   ssh-keygen -t ed25519-sk -O verify-required -f ~/.ssh/fleet-deploy -C yubikey-<serial>
   ssh-keygen -t ed25519-sk -O verify-required -f ~/.ssh/fleet-deploy-b -C yubikey-<serial>
   ```

   Each asks for the PIN and then a touch. (On a touch-only setup, drop
   `-O verify-required` from the same command and nothing else changes.)
3. Add both public halves to the declaration, from the checkout:

   ```
   nix develop -c tools/fleet keys add ~/.ssh/fleet-deploy.pub
   nix develop -c tools/fleet keys add ~/.ssh/fleet-deploy-b.pub
   ```

   Each prints `fleet: keys: added <comment>`. Then commit:

   ```
   git add hosts/fleet.json && nix develop -c git commit -m 'hosts: the two deploy keys (test: lint)'
   ```

   Acceptance: `jq '.deployKeys | length' hosts/fleet.json` → `2` — and
   add the two comment lines to `keys.toml` by hand (a comment line under
   each `[keys.basket-*]`: `# fleet-deploy enrolled <date>`).

## Join — the bootstrap

1. From the checkout, render the console bootstrap onto the USB stick
   (it refuses with exit 2 until step 3's keys exist):

   ```
   nix develop -c tools/fleet join-script > /run/media/<you>/<usb>/fleet-join.sh
   ```

   Acceptance: `head -1 /run/media/<you>/<usb>/fleet-join.sh` →
   `#!/usr/bin/env bash`; `grep -c 'sk-ssh-ed25519' /run/media/<you>/<usb>/fleet-join.sh` → `2`.
2. **On the forge's console:**

   ```
   sudo bash /run/media/<you>/<usb>/fleet-join.sh
   ```

   It ends with the two lines to write down:

   ```
   fleet-join: host key SHA256:<fingerprint>
   fleet-join: address <a.b.c.d>/<prefix> on <interface>
   ```

   Acceptance: `systemctl is-active sshd` → `active`. Until the first
   deploy replaces it, the bootstrap's sshd listens on every interface;
   the declared configuration is what binds it to the LAN address.

## Enrol

On core, from the checkout:

```
nix develop -c tools/fleet enroll forge <a.b.c.d>
```

It prompts `fingerprint (SHA256:…): ` — type the fingerprint line the
console printed. It then fetches the hardware config, the interface, the
prefix, the gateway, the nameservers, the firmware kind and the
stateVersion over one connection whose only trust root is the declared
list, writes them into the declaration, re-pins the hardware file, and
prints `fleet: enrolled forge at <a.b.c.d> (<interface>/<prefix>,
efi=<true|false>, stateVersion=<YY.MM>)`. A mismatch prints
`fleet: refused: host key fingerprint SHA256:… does not match SHA256:…`
and exits 3 with nothing written — stop and compare the console.

Acceptance: `git status --short` shows exactly `hosts/forge/hardware-configuration.nix`
(modified), `hosts/fleet.json` (modified) and `hosts/hardware-pins.sha256`
(modified); `head -1 hosts/forge/hardware-configuration.nix` →
`# Do not modify this file!  It was generated by 'nixos-generate-config'`.
The commit is the approval:

```
git add hosts/forge hosts/fleet.json hosts/hardware-pins.sha256 && nix develop -c git commit -m 'hosts: enroll forge (test: lint)'
```

## Deploy — and roll back

1. The first deploy, on core:

   ```
   nix develop -c tools/fleet deploy forge
   ```

   PIN and touch once. It builds the forge's toplevel, first printing the
   `nix store diff-closures` block against the machine's current system —
   the first time the machine's current system is not in the local store,
   so that block is skipped (`fleet: deploy: diff-closures: … is not in
   the local store; skipped`); from the second deploy on it prints the
   real diff. It then copies, sets the profile and switches, and ends
   with `fleet: deployed forge <toplevel>` and `fleet: previous: <toplevel>`.
   Acceptance:

   ```
   ssh -i ~/.ssh/fleet-deploy deploy@forge readlink /run/current-system
   ```

   prints the deployed `<toplevel>`. (Core's `/etc/ssh/ssh_known_hosts`
   pins the forge once core is next switched; until then, add
   `-o UserKnownHostsFile=<(printf 'forge,%s %s\n' <a.b.c.d> "$(jq -r .machines.forge.hostKey hosts/fleet.json)")`.)
   For a reader who knows nixos-rebuild, the same deploy is
   `nixos-rebuild switch --flake .#forge --target-host deploy@<a.b.c.d> --use-remote-sudo`.
2. **The touch, checked by hand:** run the same deploy once more with the
   YubiKey removed → `fleet: refused: … Permission denied (publickey)`,
   exit 3, before anything is copied. The deploy is impossible without the
   physical key that signed the declaration's entry.
3. Rollback is never a blind `--rollback` (there is no such flag): every
   deploy prints `fleet: previous: <toplevel>`, and rolling back is the
   deploy of that path:

   ```
   nix develop -c tools/fleet deploy forge --toplevel <the previous path the deploy printed>
   ```

## After the first deploy

1. **On the forge's console**, the LAN proxy's password. Until the file
   exists, `caddy.service` sits **failed** — expected, not a fault:

   ```
   caddy=$(systemctl cat caddy.service | grep -oE '/nix/store/[^ ]*caddy[^ /]*/bin/caddy' | head -1)
   "$caddy" hash-password
   sudo sh -c 'umask 027; printf "%s\n" "<hash>" > /var/lib/lan-access/forge.bcrypt; chgrp caddy /var/lib/lan-access/forge.bcrypt'
   sudo systemctl start caddy.service
   ```

   `hash-password` prompts and does not echo, so the password never
   reaches shell history. Acceptance: `sudo ls -l /var/lib/lan-access/forge.bcrypt`
   → `root caddy`, mode `0640` or tighter.
2. **On the forge's console**, the Forgejo admin account. Forgejo puts no
   CLI wrapper on `PATH`, so the command sets its work directories
   itself:

   ```
   fj=$(systemctl cat forgejo.service | grep -oE '/nix/store/[^ ]*forgejo-[^ /]*/bin/forgejo' | head -1)
   sudo -u forgejo env FORGEJO_WORK_DIR=/var/lib/forgejo FORGEJO_CUSTOM=/var/lib/forgejo/custom "$fj" admin user create --admin --username <owner> --email <email> --must-change-password --password '<one-time>'
   ```
3. **At the browser**, `http://<a.b.c.d>/` — the proxy's password, then
   the new account's — create the repository `<owner>/<repo>` (private,
   empty). Acceptance:

   ```
   curl -s -o /dev/null -w '%{http_code}' http://<a.b.c.d>/user/sign_up
   ```

   → `303` after the proxy credential (registration is closed).

## The mirror

1. The push key, on core:

   ```
   ssh-keygen -t ed25519 -N '' -f ~/.ssh/forge-mirror -C forge-mirror
   ```
2. **At the browser**, paste `~/.ssh/forge-mirror.pub` as a deploy key
   **with write access** on the repository's settings page.
3. Add the `mirror` block to `hosts/fleet.json` exactly:

   ```
   "mirror": {"machine": "forge", "repo": "<owner>/<repo>.git", "user": "forgejo", "keyFile": "/home/<you>/.ssh/forge-mirror", "checkout": "/home/<you>/nixos-agent-env", "onCalendar": "hourly", "runAs": "<you>"}
   ```
4. Append the push URL to `githooks/allowed-remotes.txt` (one more line —
   the pre-push hook refuses a push to anything not listed):

   ```
   ssh://forgejo@forge/<owner>/<repo>.git
   ```
5. Stage both and commit, then switch core and start the timer (a switch
   never starts a newly enabled user timer in a logged-in session):

   ```
   git add hosts/fleet.json githooks/allowed-remotes.txt && nix develop -c git commit -m 'hosts, githooks: the forge mirror (test: lint)'
   sudo nixos-rebuild switch --flake ~/nixos-agent-env#core
   systemctl --user start fleet-mirror.timer
   ```

   Acceptance:

   ```
   systemctl --user start fleet-mirror.service && systemctl --user status fleet-mirror.service
   git ls-remote ssh://forgejo@forge/<owner>/<repo>.git
   ```

   → `status=0/SUCCESS`, and `git ls-remote` lists `refs/heads/main` and
   `refs/tags/live-gen28-2026-09-03` (the `live-*` tag the mirror pushes).
   Helm's timers tile does not audit this timer (its list is fixed), so
   check it yourself: `systemctl --user status fleet-mirror.service`.

## The forge's backup

The forge carries its own backup instance — follow `docs/runbooks/backup.md`
"The forge" (question 3 = `desktop`: the forge keeps a GNOME session with
you logged in, because the Proton Drive push is a user unit that reads the
CLI's login from your keyring). One-time setup, **on the forge's desktop
session**:

```
install -d -m 0700 ~/.config/restic
umask 077; printf '%s\n' '<a new restic password>' > ~/.config/restic/password
proton-drive auth login
```

The password is a new one (Proton Pass plus paper, like core's — never
core's own password). Acceptance, on the forge after the first night:

```
systemctl status restic-backups-core-local.service
proton-drive filesystem list /my-files/backups/forge
```

→ `status=0/SUCCESS` (the module names the job `core-local` on every
host) and the remote lists `config`, `snapshots`.

## Rotating or removing a deploy key

The machine's authorized keys are the declaration: delete the line from
`deployKeys` in `hosts/fleet.json`, commit, and the next `fleet deploy
forge` removes it from the machine. If both YubiKeys are lost, so are the
keys — start again from the console (`fleet-join`, the Join section
above).

## What never happens

- Core never runs an SSH server (asserted at evaluation).
- Nothing is trusted on first use: every SSH the tool opens carries the
  declared host key — there is no first-contact acceptance, no
  `known_hosts` prompt.
- The tool trusts only `hosts/fleet.json`: no other source of host keys,
  addresses or identities.
- The forge never pulls from core: the mirror is the only link, and it is
  always core → forge, outbound from your user session.
- No real address appears in a published file: the forge's LAN address
  lives only under `hosts/`, which is withheld from the public repo.
