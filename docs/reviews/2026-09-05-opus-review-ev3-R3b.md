## Findings

- **major** `tests/helm/test_collect.py:388-405 (pkgs/helm/collect.py:315)` — The user-scope half of tile_timers still pins neither the unit it queries nor the systemd scope — the same vacuity the R3 gate rejected as major M6 for backup-parity, left in place for the branch that covers the live host's user timers. test_timers_service_timeout_is_fail keeps its local `table` fake, which dispatches on `argv[0] == "systemctl"` plus `argv[-1].endswith(".timer"/".service")` and never looks at `--user` or at the unit name. Two mutations survive all 145 tests: M7 `_unit_result(["--user"], service)` -> `_unit_result([], service)` ('145 passed in 13.18s') and M12 `_unit_result([], "not-a-real-unit.service")` ('145 passed in 13.20s'). This is live-relevant and falsifiable: nixosModules/helm.nix:409-415 puts proton-drive-push.timer, helm-collect.timer and helm-flake-check.timer in `timers.user`, and I probed the live host read-only — `systemctl show -p Result -p ExecMainStatus helm-flake-check.service` (system scope, a USER unit name) prints `Result=success` / `ExecMainStatus=0`. So a wrong-scope implementation reports a clean success for a user unit that was actually killed, i.e. the tile goes green in exactly the 'nightly flake check killed by its 2 h timeout' case the plan's Interfaces name as the reason this feature exists. The commit message's claim that 'parity and timers tests pin the unit and scope' is therefore only half true. R3b closed the parity and system-scope holes but not the symmetric user-scope one. **Fix:** Replace the local `table` in test_timers_service_timeout_is_fail with the helper the round already generalised: `monkeypatch.setattr(collect, "run", systemctl_fake({"helm-flake-check.timer": _unit_show("success"), "helm-flake-check.service": _unit_show("timeout", "0", active="failed", nxt="")}, scope="user"))`. The scope="user" arm already asserts `argv[:3] == ["systemctl", "--user", "show"]`, and keying on the unit name makes an unlisted (wrong) unit fall through to the default `_unit_show("success")`, so both M7 and M12 turn red. Re-run `pytest tests/helm -q` and re-verify both mutations die.
- **minor** `pkgs/helm/collect.py:325-330` — The `"; ".join(parts)` that composes the two offender groups is unpinned: mutation M10 (`return "fail", parts[0], detail`) leaves 145 tests green, because no test exercises an unarmed timer and a failed service in the same run. With both present the tile would silently drop one group from the summary — the operator would see 'not armed: b.timer' and never learn a service had also died. The tile still reads fail, so this is cosmetic-but-informational, not a wrong verdict. **Fix:** Extend test_timers_inactive_is_fail (or add a sibling) so one timer is unarmed and another timer's sibling service reports e.g. 'timeout', and assert the exact summary `"not armed: b.timer; failed: a.service: timeout"`. That kills M10 and pins the ordering of the two groups.
- **minor** `pkgs/helm/collect.py:165-167 (mirrored in tests/helm/test_collect.py:365-368)` — The comment added to justify the `""` arm states a systemd behaviour that is false: 'a unit that has never run reports `Result=success` but no ExecMainStatus line, so systemctl leaves the field empty'. Probed read-only on the live host: `systemctl --user show -p Result -p ExecMainStatus helm-flake-check.service` (a never-run user unit) prints `Result=success` / `ExecMainStatus=0`, and so does the same query for a unit name that does not exist at all. ExecMainStatus is an integer property and is always emitted. An empty `status` in _unit_result can therefore only arise when the property line is absent entirely (systemctl produced no output), in which case `result` is also "" and the first clause `result != "success"` already reds the tile. So test_parity_empty_exec_status_is_ok pins a state the host cannot produce, on a stated rationale that is wrong — it kills mutation M1, but it documents fiction. (The R3 gate offered this fixture as one of two acceptable options, hence minor, not major.) **Fix:** Either correct both comments to say what the arm actually guards ('a systemctl invocation that emitted no ExecMainStatus line at all — defensive; the missing-Result clause above already covers the real cases'), or take the review's other option: drop the `""` arm, delete test_parity_empty_exec_status_is_ok, and note in _unit_result's docstring that a missing Result line already reds the tile.
