## Findings

- **minor** `pkgs/evidence/SCHEMA.md:6` — E1b changed a reader contract that E5's tiles and E9's bundle will build on — latest-check now resolves an equal-ts tie to the later-appended row — but that rule is documented only in a code comment at pkgs/evidence/evidence.py:97-98. SCHEMA.md is the file the plan calls "the contract every other task writes against", and its reader paragraph ("Readers: … A reader skips a torn line …") says nothing about tie resolution. A downstream implementer reading only SCHEMA.md would not know that two observations in the same second are ordered by append position. **Fix:** Add one sentence to SCHEMA.md's reader paragraph: "For one (name, rev), latest-check returns the row with the greatest ts; on equal ts the later-appended row wins." Separately, the sentence added at SCHEMA.md:6-7 ("The envelope (v, ts) is written after the writer's row") describes dict-construction order, which is invisible in the file because append() serialises with sort_keys=True — say "the envelope overrides any v or ts in the writer's row" instead, so nobody infers that key order in the JSONL is meaningful.
- **minor** `tests/evidence/test_evidence.py:148` — The ts-primary half of latest_check is unpinned: replacing the whole condition at evidence.py:101 with `if True:` (latest_check becomes rows[-1], file order only) leaves 13/13 green (mutation M4). Every test appends rows for a given (name, rev) in non-decreasing ts order, so no test can distinguish "greatest ts wins" from "last row wins". The behaviour E1b added is correct and its own mutations die (M3, M5), but the property the new comment claims — ts first, file order only as tie-break — is only half observed. **Fix:** Add two appends to test_latest_check_same_ts_prefers_later_row: after the flake-check pair, append a THIRD flake-check row with an earlier ts (e.g. ts="2026-09-05T11:00:00Z", ok=True) and assert latest_check still returns the ok=False row. That kills M4 and costs one assertion.
