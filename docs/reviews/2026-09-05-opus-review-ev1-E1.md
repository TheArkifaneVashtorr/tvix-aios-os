## Findings

- **minor** `pkgs/evidence/evidence.py:97` — latest_check tie-breaks the wrong way. `max(rows, key=lambda r: r["ts"])` returns the FIRST maximal element, and now_iso() has 1-second resolution, so two observations for the same (name, rev) written in the same second make `latest-check` report the OLDER row. Proven with the real CLI: two `record-check --name x --rev <40a>` calls (--ok then --fail) both landed at ts 2026-09-05T14:03:44Z, the file holds ok [true, false] in that order, and latest_check returned ok=true. The failure direction is unsafe for D4/E5 (a stale green masks a fresh red in the flake-check tile) and for E9's bundle. Inherited verbatim from the plan's Step 3 code block, and the obvious mutation (max→min) IS killed — hence minor, not major. The suite dodges it: test_cli_record_check_ok_and_fail sets up exactly this same-second pair but asserts on ev.read order instead of latest_check. **Fix:** Make the newest row win ties by falling back to file order: `return max(enumerate(rows), key=lambda t: (t[1]["ts"], t[0]))[1] if rows else None` (or sort stably and take rows[-1]). Add a case to test_latest_check_picks_newest_for_name_and_rev with two rows sharing one ts, asserting the later-appended one comes back. Because this is a contract E5/E9 build on, amend the plan's E1 block rather than fixing it silently.
- **minor** `pkgs/evidence/evidence.py:54` — The caller's row overrides the envelope. `full = {"v": VERSION, "ts": ts or now_iso(), **row}` splats the caller's object last, so `evidence record checks --json '{"kind":"check","v":99,"ts":"1970-01-01T00:00:00Z"}'` records {"kind": "check", "ts": "1970-01-01T00:00:00Z", "v": 99} — verified by running the CLI. That breaks the invariant SCHEMA.md:5 states as the contract for every downstream reader ("every row: {\"v\":1,\"ts\":…}"), and a backdated ts combines with finding #1 to let a writer pin latest-check to a chosen row. No test guards the precedence: mutation M21 (envelope last) leaves 11/11 green. Also plan-inherited. **Fix:** Put the envelope last: `full = {**row, "v": VERSION, "ts": ts or now_iso()}` — I ran this and the suite stays 11/11 green. Add an assertion that `record --json '{"kind":"x","v":99}'` still writes v=1. The `ts=` keyword argument keeps working, since it is a parameter rather than a row key.
- **minor** `pkgs/evidence/evidence.py:60` — `os.fchmod(fd, 0o640)` cannot be tested in isolation because the O_CREAT mode on the line above already yields 0640 under this repo's umask: dropping the fchmod (M7) leaves 11/11 green, and widening only the open mode (M13) also leaves 11/11 green. The trailing comment ("the umask must not widen or narrow the group bit") asserts a property the suite cannot observe. This is NOT a vacuous test — M12 (widening both) is killed, so the 0640 outcome is pinned — only the redundancy is unverified. **Fix:** Either drop the claim from the comment, or make it real: run one append in a subprocess under a hostile umask (os.umask(0o077)) and still assert stat.S_IMODE == 0o640, which would then kill M7.
