## 3. Sandbox and permission parity (the matrix; every denial)

### 3a. Where the seat's permission state actually comes from

1. **reader-stated** — The only knob is the environment variable `DSH_PERMISSION_MODE`, read once by `dsh-openrouter`'s wrapper (`permission=${DSH_PERMISSION_MODE:-workspace-write}`) and consumed inside `@deepseek-ai/dsh-base`'s `cordis.patch.yml`, which sets `sandbox-policy.mode` (default `workspace-write`) and `approval.policy` (`never` iff the mode is `danger-full-access`, else `ask`).
2. **reader-stated** — Nothing in the seat path passes it. `grep -niE 'permission|sandbox' pkgs/seat/seat-submit.py pkgs/seat/seat-run.py` → zero hits in both; `seat-drive.sh`'s drive-mode `submit_args` carries only `--workspace --dsh-home --model --effort --port` (+`--no-start`); `grep -rniE 'DSH_PERMISSION_MODE|--permission' tools/factory/seat/` → zero hits. No settings file has a permission key either: `settings.yaml` carries only `ui-onboarding` and `agent-default-model`, and both profiles' `cordis.yml`/`cordis.patch.yml` are empty `[]`.
3. **inferred** (from 1–2) — The drive session is born `workspace-write`/`ask` because the compiled-in default is the only thing that ever applies. There is no configuration lever anywhere in the deployed tree; only the env var at process launch.
4. **reader-stated** — Every fresh root session is born `permission/preset workspace-write` → `sandbox/mode workspace-write` → `approval/policy ask` at seq 0–2, *including after a restart* — an escalation never survives into a new root session. Two escalation events exist in the whole drive home (`session-1de16652` at 18:48:22Z, `session-fab3a31b` at 18:59:30Z); the third root session (`e9f65214`, opened 21:50:01Z) never escalated at all.

All four asks resolved with no intervening `user/message`; the operator's own manual flip from `ask` to `never` is a later, separate event (`The approval policy changed from "ask" to "never" (changed by the user).`).
6. **reader-stated** — Subagents inherit, they do not default: `dsh-subagent`'s `captureDelegatedPolicyOverrides` copies the parent's *current* sandbox override and pins `approvalPolicy` to `'never'` **unconditionally** ("regardless of the parent's own policy", its own doc comment). ## 7. Factory mechanics for batching plans (what collides)

1. **measured** — There is no batch verb. `grep -n "batch\|several plans\|multiple plans\|concurrent plan"` over the planning-agent spec and the factory-dispatch plan returns nothing. Batching composes out of per-plan primitives.
2. **measured** — `plan.js` plans **one spec per invocation**: `.claude/workflows/plan.js:60` — `if (!A.date || !A.name || !SCRATCH || !A.spec) throw new Error('plan: args need date, name, scratch, spec')`; `:61` requires `out` unless `judgeOnly`. Its five phases are Packet (5 Sonnet readers), Draft (Fable), Judge (2 Sonnet + 1 Opus, blind, 14-row rubric), Revise (Fable, ≤2 rounds), Ship (Sonnet).
3. **measured** — The Packet phase **refuses to draft on an unsound graph**: `.claude/workflows/plan.js:308` — `if (!mech || mech.checkEmpty !== true)` throws, where `checkEmpty` is true only when `tasks.py check` printed nothing (`:185`). A partial packet (fewer readers than `READERS.length`) throws too.
4. **measured** — Ship always writes `docs/reviews/plan-judgements/<date>-<name>.md`; only on `decision === 'dispatch'` does it copy the draft to `docs/superpowers/plans/<out>`, paste `tasks.py check`, `conflicts`, `waves --next` and a `factory-dispatch … --dry-run`, and write a concept file. In replan mode it first requires every prior `### ` heading to survive byte-identically: `.claude/workflows/plan.js:411` runs `comm -23 <(grep '^### ' <plan> | sort -u) <(grep '^### ' <draft> | sort -u)` and aborts if it prints a line.
5. **measured** — The graph is built from **every typed plan at once**, not one at a time: the repo builder globs `docs/superpowers/plans/*.md` and folds all tasks into one list keyed by chain root.
6. **measured** — Therefore the hard batching constraint is key-namespace disjointness. `pkgs/evidence/tasks.py:1634-1642` refuses the same key defined in two plans: `errors.append(f"tasks: {name}/{key} defined in {' and '.join(plans)}")`. **Inferred** (from 3 + 6): two plans in a batch that reuse a key make `tasks.py check` fail, which makes `plan.js`'s Packet phase refuse to draft anything at all.
7. **measured** — The cross-plan file-overlap checker already exists and is exactly this shape: `pkgs/evidence/tasks.py:1349` `def conflicts(repo_graph)` compares every pair of *open* tasks from *different* plans of the same repo and reports a row per overlapping `touches` path.
8. **measured** — Dispatch is one plan per invocation: `factory-dispatch <run> <repo-path> <plan-file>` asks `tasks.py --root <repo-path> waves --repo NAME --plan <basename> --next` and launches through `factory-wave`, doing no graph logic of its own. Batching N plans against one repo is N separate `factory-dispatch <run_i> <repo> <plan_i>.md` calls, each with its own run name.
