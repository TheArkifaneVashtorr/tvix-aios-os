# Research digest 2026-09-02 — Helm v1: switching profiles and opening workspaces without code

*Read-only research by a Sonnet agent, 2026-09-02 late evening, against the host pin nixpkgs ac62194c and the live host. Side effect to note: probing `claude-desktop --help` launched a second desktop window (no such flag exists). Feeds docs/superpowers/specs/2026-09-02-helm-v1-switch-design.md.*

## Findings 1-5

**1. Specialisations at the pin**
- `nixos/modules/system/activation/specialisation.nix` (source at the pin): each `specialisation.<name>.configuration` is built via `extendModules`/`noUserModules.extendModules` into a **full, independent `system.build.toplevel`** (own `/etc`, own activation script), then `system.systemBuilderCommands` does `ln -s ${path} $out/specialisation/${name}` — so `$out/specialisation/<name>` is a symlink to a *complete* separate toplevel, not a diff.
- The module's own doc comment gives the manual runtime command: `sudo /run/current-system/specialisation/fewJobsManyCores/bin/switch-to-configuration test` (specialisation.nix, options.specialisation description). `switch` works identically to `test` but also relinks `/run/current-system` (see below).
- `activation-script.nix:77-79`: `ln -sfn "$(readlink -f "$systemConfig")" /run/current-system` — this line runs as part of **every** toplevel's own activation script, including a specialisation's. So running a specialisation's `switch-to-configuration switch` **does** repoint `/run/current-system` at the specialisation's own store path (confirmed distinct from the base: each specialisation toplevel carries its own `/etc`, so an `environment.etc."helm/profile"` file set to a different string per specialisation gets correctly swapped in by ordinary `/etc` activation — no special-casing needed).
- `nixos-rebuild.sh:956-970`: with `--specialisation <name>`, `pathToConfig` is still `$profile` (`/nix/var/nix/profiles/system`, already updated to the **new base** generation earlier in the script), but the command actually executed is `$pathToConfig/specialisation/$specialisation/bin/switch-to-configuration switch`. So `nixos-rebuild switch --specialisation <name>` **does** set the boot-default *profile* to the new base generation (bootloader menu entry = base, with specialisation sub-entries per the comment in specialisation.nix about children only being reachable when the parent is boot default), while the *running* system is left activated on the specialisation. A reboot without re-selecting the specialisation in the boot menu lands you back on base.
- Going back to base at runtime: `/run/current-system/specialisation/<name>/bin/switch-to-configuration` only exists reachable via the base toplevel's own symlink tree; once you're inside a specialisation, `/run/current-system` points at the specialisation, and its `/etc`, not the base, so the reliable "back to base" command is the profile's own binary: `/nix/var/nix/profiles/system/bin/switch-to-configuration switch` (this is stable regardless of what's currently active, since it's the profile generation entry point).
- Nothing in vanilla NixOS records "which specialisation is active" anywhere — confirmed live on this host: `ls -la /run/current-system/specialisation` is empty (this flake defines no specialisations yet), and `/nix/var/nix/profiles/system -> system-22-link`. Given the activation-script.nix:77-79 finding, the proposed `environment.etc."helm/profile"` marker (different literal string per `specialisation.<name>.configuration`) is sound and will reliably update on every switch, in or out of a specialisation, because `/etc` activation is unconditional.
- Runtime effect on services: `switch-to-configuration` only restarts/reloads units whose unit files actually changed (comment at switch-to-configuration.pl:53-56, "handle `restartIfChanged`/`reloadIfChanged`"); GNOME session, Wayland compositor and logind are user/session-scoped and untouched by a `switch` unless a system unit they depend on changes; NVIDIA kernel module and podman are unaffected unless the specialisation changes their config (kernel/initrd are never touched by a specialisation switch, so no reboot is required, matching the design's assumption).

**2. Privilege boundary**
- Live polkit version on this host: `polkit-126` (`nix eval --raw nixpkgs#polkit.version` → `126`; confirmed installed at `/nix/store/37k80sq6bvhzgbx01pvk3blcfn65k4ha-polkit-126`).
- polkit switched to the duktape JS engine at 121+ (ES5 subset only — e.g. no `Array.includes`), confirmed by web research (Arch bug FS#73502, meta-oe patch series). This host's own `/etc/polkit-1/rules.d/10-nixos.rules` already uses only ES5-safe constructs (`indexOf`, `isInGroup`), so existing NixOS-generated rules are duktape-safe.
- `action.lookup("unit")` for `org.freedesktop.systemd1.manage-units` is a documented, supported systemd feature (systemd commit `88ced61` "core: pass details to polkit for some unit actions" passes `unit` and `verb` details to polkit) and is unaffected by the mozjs→duktape switch (both engines support property lookup / basic conditionals). A working rule shape: `polkit.addRule(function(action, subject){ if (action.id == "org.freedesktop.systemd1.manage-units" && action.lookup("unit") == "helm-switch@base.service" && subject.user == "dalhaka") return polkit.Result.YES; })` — this needs one rule per allowed instance (or a regex/prefix check on the unit string) since duktape has no glob helper.
- Recommendation: **polkit rule scoped to `helm-switch@*.service` + `subject.user`**, not sudo NOPASSWD. Reasoning: polkit's rule lives in `/etc/polkit-1/rules.d` (declaratively managed by the NixOS module via `security.polkit.extraConfig`), ties the grant to `systemctl --user`-callable `manage-units`, and needs no setuid wrapper or password prompt; a sudo NOPASSWD wrapper is a strictly larger attack surface (arbitrary root exec if the wrapper script has any parsing bug) and isn't composable with the templated-unit + fixed-allowlist requirement as cleanly.

**3. Backend CSRF / DNS rebinding**
- OWASP's current CSRF Cheat Sheet (fetched via search, Dec 2025 revision) recommends the **Fetch Metadata method as a complete, standalone defense**: reject any state-changing request unless `Sec-Fetch-Site` is absent or `same-origin`, with `Origin`/`Referer` header verification as the required fallback for older browsers.
- Chrome's Private Network Access spec (`developer.chrome.com/blog/private-network-access-update-2024-03`) shows Chrome now preflights cross-origin requests from public pages into private/loopback address space and requires the server answer `Access-Control-Allow-Private-Network: true`; this is a real defense-in-depth layer but **Firefox does not implement PNA**, so it cannot be relied on alone (this host's browser is Firefox per the Helm design doc).
- Recommended concrete checks for the stdlib `http.server` endpoint: (a) reject unless `Sec-Fetch-Site: same-origin` (falls back to `Origin` header exact-match against `http://127.0.0.1:<port>` when Fetch Metadata is absent); (b) reject unless `Host` equals the bound `127.0.0.1:<port>` (defeats DNS rebinding — a rebound hostname sends `Host: attacker.example`, not the IP:port); (c) POST-only, and require a custom header (e.g. `X-Helm: 1`) so any cross-origin fetch triggers a CORS preflight that the server's `OPTIONS` handler simply doesn't answer with `Access-Control-Allow-Origin`, blocking it browser-side; (d) a per-boot random token written 0600 to a file only the operator's page-serving process can read and embedded in the served HTML, checked on every mutating request.

**4. Launcher**
- Terminal present: `kgx` (GNOME Console) is installed; no alacritty/foot/kitty found (`ls /run/current-system/sw/bin | grep -iE 'terminal|console|kgx|...'` → `fgconsole kgx showconsolefont spawn_console xdg-terminal`). `kgx -e '<cmd>'` or `xdg-terminal` is the way to launch a shell running `nix develop` in a directory.
- Live on this host, `systemctl --user show-environment | grep -E 'WAYLAND|DBUS|DISPLAY'` returns `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus`, `DISPLAY=:0`, `GNOME_SETUP_DISPLAY=:1`, `WAYLAND_DISPLAY=wayland-0` — confirmed present in the user manager environment, so a user unit (e.g. the Helm backend, or a unit it triggers) **can** reach the Wayland/X display and D-Bus session without extra plumbing.
- Claude Desktop: `hosts/core/claude-desktop.nix` enables it as the operator's unconfined day-to-day interface; `claude-desktop --help` did not print help — it launched the actual Electron GUI (unintended side effect of this read-only probe; the app is still running as PID 289789+ under the operator's session — I could not kill it, the sandbox blocked `kill`, so the operator may want to close that window manually). Web research (GitHub issue anthropics/claude-code#54614) confirms there is **no supported CLI flag or deep link to open Claude Desktop directly into a Code session on a given folder** — the only reliable path today is the terminal workaround `cd <path> && claude`, which is exactly what Helm's launcher already plans to do via `kgx -e`.

**5. Basket mounting**
- `pkgs/basket/basket.sh:132-190` `cmd_mount`: `[[ "$(id -u)" -eq 0 ]] || die "mount: must run as root"` (line 153) — mounting is **hard-gated to root**, no userns fallback; it does `mount -t tmpfs`, decrypts the payload with age via `cmd_decrypt` into the tmpfs, then `mount --bind` into `/run/baskets/<id>` and remounts read-only for `ro` baskets.
- Because it's unconditionally root-only and involves decrypting age-encrypted content (the design doc for workspaces says recipients = YubiKeys), a launcher cannot mount a basket passwordlessly without either (a) a polkit/root-unit path parallel to the specialisation switch that also demands the YubiKey touch for decryption, or (b) staying an operator-run manual step. Given the YubiKey-gated decryption, **mounting must stay operator-initiated** (the launcher can shell out to `basket mount` via the same root unit pattern, but the YubiKey touch prompt is unavoidable and shouldn't be silently bypassed) — this matches the claude-workspaces-design doc's assumption that `basket seal`/`mount` are explicit CLI operations.

## Recommended v1 architecture

A single root systemd template unit `helm-switch@.service` (ExecStart runs a fixed, allowlisted script keyed by `%i` — one of `base`, `gaming`, `media` — that execs the corresponding `switch-to-configuration switch` binary, either `/run/current-system/specialisation/<name>/bin/switch-to-configuration` or `/nix/var/nix/profiles/system/bin/switch-to-configuration` for base) is started by the unprivileged operator user solely via a scoped `security.polkit.extraConfig` rule matching `action.id == "org.freedesktop.systemd1.manage-units" && action.lookup("unit").indexOf("helm-switch@") == 0 && (action.lookup("unit") == "helm-switch@base.service" || ...) && subject.user == "dalhaka"` (enumerate the fixed set explicitly — duktape has no glob). The Helm web backend itself runs as an **unprivileged user** systemd service (loopback `http.server`), and for a profile switch calls `systemctl --user` is wrong (unit is system-scope) — it shells `systemctl start helm-switch@<name>.service`, which polkit authorizes without a password because of the rule above. Every mutating request must pass the Sec-Fetch-Site/Origin + Host + custom-header-forces-preflight + per-boot-token checks from Q3 before it's allowed to call `systemctl start`. Active-profile marker: `environment.etc."helm/profile".text = "<name>"` set per specialisation (and `"base"` in the top-level config), read straight off disk by the status page — reliable because of the activation-script.nix:77-79 `/etc` swap-on-every-activation behavior confirmed above. Workspace launch (goal B) is a second, separate unprivileged action: the backend runs `kgx -e 'bash -lc "cd <repo> && nix develop -c ${SHELL:-bash} -ic \"claude\""'` as the operator (no root unit needed — `systemctl --user show-environment` confirms `WAYLAND_DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` are already in the user manager's env, so `kgx` launched by the user service reaches the real GNOME session). Basket mounting stays an explicit, YubiKey-gated operator step, not something the launcher does silently.

## Risks / unknowns

- This flake currently defines **zero specialisations** (`/run/current-system/specialisation` is empty on the live host), so none of the switch-command claims above have been exercised live — they rest on nixpkgs source reading plus general NixOS specialisation semantics, not on-host verification.
- Boot-menu behavior for specialisations (whether `systemd-boot`/grub expose a submenu entry per specialisation only when parent is boot-default) was read as a code comment in specialisation.nix but not traced into the bootloader-builder modules; worth confirming before relying on "boot into gaming directly" as a fallback.
- polkit `action.lookup("unit")` behavior specifically for `systemctl start <template>@<instance>.service` calls originating from a non-root D-Bus caller was corroborated via web search (a Debian wiki / systemd commit citation), not tested against this exact polkit-126 build.
- I accidentally launched the real Claude Desktop Electron app while probing `--help` (no `--help` flag exists) and could not kill the resulting process (sandbox blocked `kill`) — the operator may see a stray Claude window open.
