(fetched 2026-09-03) https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md
- **Headless mode.** Documented headless invocation: `dsh --profile headless "job"` — boots a fresh persisted session, prints the final answer, and exits nonzero on invalid commands/config/boot failures, zero on success. Other flags: `--profile <name>` (boots $DSH_HOME/profiles/<name>; `dsh web` is shorthand for `--profile web`), `--dump-default-config`, `--dump-config`, `--patch` for config overlays. No explicit `--print`/`-p`/structured JSON-result flag was found in what I could fetch — only 'print the final answer' as plain text; a dedicated machine-readable JSON output flag for headless task results is UNVERIFIED. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/index.md
- **Headless approval behavior.** By design, in a headless composition dsh resolves 'ask' permission decisions to 'deny' — an unattended agent cannot self-approve mid-run. To get a fully unattended run you must pre-select a permission preset before starting: read-only, workspace-write, or danger-full-access (the last is explicitly unsandboxed and approval-free — described in third-party commentary as the 'yolo equivalent'). This specific claim about headless ask→deny came from a WebSearch AI-summary (not a page I fetched and read directly) citing an unnamed 'development guide' — treat as PLAUSIBLE, not independently confirmed by me. (fetched 2026-09-03) https://agenticcontrolplane.com/controls/dsh
- **Model endpoint configuration.** Custom OpenAI-compatible providers are configured either via the Settings UI or directly in $DSH_HOME/settings.yaml under `llm-pi-ai.providers.<id>` with fields: apiKeyEnv (env var name holding the key), api (protocol, e.g. 'openai-completions'), baseURL, and models (list of model ids). Example shown in docs uses a generic 'my-gateway' example, not OpenRouter by name, but the mechanism (arbitrary baseURL + openai-completions protocol + API key via env var) is generic and would work for https://openrouter.ai/api/v1 with a model id such as a deepseek model slug. OpenRouter itself is not named anywhere in the official docs I fetched. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/providers.md
- **Proxy and CA cert support.** dsh reads HTTPS_PROXY/HTTP_PROXY (and ALL_PROXY as fallback) at launch for all outbound requests — model calls, web search, page fetches, MCP servers over HTTP. NO_PROXY (domain/suffix, not CIDR) is honored; localhost is auto-bypassed. SOCKS proxies are NOT supported (HTTP proxy port required). Proxy URLs can embed credentials (http://user:pass@host:port). NODE_EXTRA_CA_CERTS is honored for custom/corporate CA certs, but must be exported before the `dsh` process starts (Node reads it only at process start). Settable via shell profile or $DSH_HOME/.env. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/network-proxy.md
- **Built-in tool set.** Base/minimal-agent-preset tools documented: bash (shell exec, sandbox-confined to session workspace + platform temp roots), str_replace_editor (file edit), web_search (native DeepSeek adapter), web_fetch (runs in every sandbox/approval mode without per-call confirmation; rejects non-public destinations e.g. internal IPs). File read/write and search/grep beyond str_replace_editor were referenced only generically ('file read/write/edit... exist elsewhere') — a complete enumerated tool list was not found in what I could fetch; treat the full inventory as UNVERIFIED beyond these four. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/apps/cli/reference/README.md
- **Tool permission pre-approval.** Tools are governed by a pre-execute waterfall per scope: allow (proceeds), deny (errors), ask (requires an approval service to return 'allowed-once', else denied). A `ToolRestriction` interface supports per-scope allow/deny arrays of tool names, which is the mechanism for pre-approving specific tools ahead of a headless run. Given headless resolves 'ask' to 'deny', pre-approval for unattended runs effectively means choosing the workspace-write or danger-full-access sandbox preset up front, not a per-call approval queue. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/tools.md
- **Sandbox plugin interface.** A sandbox plugin implements the `SandboxProvider` seam with one required method: `confine(argv, policy)`, which wraps a command's argv to run confined under `policy` on the host and returns a `ConfinedArgv` (wrapped argv, enforcement level, denial signatures, runner failure rules), or throws `SandboxUnavailableError` if no backend exists. The default/built-in implementation is `dsh-sandbox-local`, covering Linux bwrap/Landlock, macOS Seatbelt, and a Windows ACL restricted-token backend. Three file-effect modes: read-only, workspace-write, danger-full-access (bypasses confinement). Enforcement is reported as 'full' or 'partial' (older kernel ABIs / Windows ACL gaps). The docs explicitly state network and process visibility are OUT of the sandbox's vocabulary — i.e. dsh's own sandbox plugin does not do network egress control; that has to be provided externally (e.g. by the systemd unit's network namespace / nftables, as this repo already does for other agents). (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/sandbox.md
- **Telemetry / phone-home.** Session telemetry is OFF by default as of a 2026-08-10 fix (documented in an in-repo incident note, .agents/notes/implemented/feature/2026-08-10-telemetry-default-off.md): earlier internal builds had two feeds (a session OTel backend and a 'dsh-sdk launcher' feed) reporting by default, potentially including full session content, tool data, prompts, and workspace paths, to a 'baked-in production endpoint' whose hostname is NOT disclosed in the docs I could fetch. The fix requires explicit opt-in via `DSH_TELEMETRY_MODE` (DISABLED/unset = no telemetry, FEEDBACK_ONLY = local only, FULL = OTLP/HTTP log export). `DSH_TELEMETRY_DISABLED` (any non-empty value) is a hard override that disables telemetry even if a profile requests FULL. Since telemetry defaults to disabled and its default state cannot be silently re-enabled by project config, no telemetry host needs to be allowlisted for a stock headless run as long as DSH_TELEMETRY_MODE is left unset/DISABLED. The actual telemetry endpoint hostname remains UNVERIFIED — I found no page naming it. (fetched 2026-09-03) https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/.agents/notes/implemented/feature/2026-08-10-telemetry-default-off.md

## Recommendation (researcher)
Smallest viable headless dsh unit for this repo, modeled on the existing egress-broker pattern already in this flake:

1. Package: build @deepseek-ai/dsh from the apps/cli workspace package of github.com/deepseek-ai/deepseek-harness (pin an exact commit/tag, not a moving branch — it's a fast-moving developer preview) using nixpkgs' buildNpmPackage/pnpm equivalent. Confirm the pinned nixpkgs' Node 22.x satisfies the workspace's `^22.19.0 || >=24.0.0` engines constraint before committing to it; if it doesn't, either bump the Node point release in the nixpkgs-host pin or pin dsh to an npm dist-tag built against an older engines range.

2. Run as: a oneshot systemd unit (mirroring the broker-consumer pattern in cowork.nix — join with `NetworkNamespacePath` pointed at an `egress-broker` instance) so the unit's only route out is the TLS-terminating broker, allowlisted by SNI to openrouter.ai (and nothing else — no telemetry host needed since telemetry is opt-in and defaults off).

3. Repo snapshot: bind-mount (read-write, workspace-write sandbox preset) a throwaway git worktree/tmpfs copy of the target repo into the unit's private mount namespace — never the live tree — so the diff it produces is easy to capture and the run can't touch anything outside that copy. dsh's own sandbox plugin (dsh-sandbox-local, Linux bwrap/Landlock) handles filesystem confinement inside the unit; it does not do network confinement itself, so the systemd/netns/nftables layer this repo already builds for the broker is still required and is the correct place to enforce "openrouter.ai only."

4. Invocation: `DSH_TELEMETRY_MODE=DISABLED DSH_TELEMETRY_DISABLED=1 HTTPS_PROXY=https://<broker-addr> NODE_EXTRA_CA_CERTS=<broker CA bundle path, matching this repo's existing ca-bundle.crt pattern> dsh --profile headless "<task>"` against a $DSH_HOME/settings.yaml preconfigured with a custom provider block (baseURL https://openrouter.ai/api/v1, api: openai-completions, apiKeyEnv pointing at a secret injected via systemd LoadCredential, not a literal key file) and the target model id. Because headless mode resolves any 'ask' tool-approval to deny (per the third-party summary — verify this against the CLI's own --help/source before depending on it for automation), you must pick the permission preset explicitly ahead of time: workspace-write is the right choice here (never danger-full-access) so the run can edit/build inside the mounted repo copy without needing live approval, while still being denied anything outside it.

5. Output: capture stdout (the printed final answer = the summary) and `git diff` inside the mounted copy after the run exits, then tear the copy and netns down — exactly the same discard-after-use shape as this repo's basket lifecycle, just applied to a repo snapshot instead of a classified basket.

Before wiring this into the flake for real, two things need a first-hand check rather than doc-summary trust: (a) run `dsh --help` / `dsh --profile headless --help` directly from a built package to nail down the exact non-interactive flag surface (a dedicated JSON output flag, the permission-preset flag name) since I could only confirm these from docs and a secondary WebSearch summary, not primary --help output; (b) treat the entire secondary "dsh ecosystem" of blogs and unofficial plugin repos surfaced by search as noise — do not source install steps, permission plugins, or config examples from dsharness.io / deepseekharness.io / deepseekagent.io / ofox.ai / atlascloud.ai / agenticcontrolplane.com / open-harness.net / computingforgeeks.com / verdent.ai / NanmiCoder or Jiao-XXX's GitHub repos; only github.com/deepseek-ai/deepseek-harness and registry.npmjs.org are canonical.

## Corrections after first-hand checks (2026-09-03, orchestrator)

- **Proxy claim was wrong.** dsh 0.1.2-rc.1 does not route model calls
  through `HTTPS_PROXY`: against a local logging proxy with an unroutable
  endpoint it attempted a direct connection and never sent a CONNECT. The
  `HTTPS_PROXY`/`NODE_EXTRA_CA_CERTS` names in `dsh-app-boot` are a list of
  variables a discovered `.env` file may not set, not proxy support. Node
  22.20's `NODE_USE_ENV_PROXY=1` makes global `fetch` use undici's
  `EnvHttpProxyAgent`; with it dsh tunnelled every request (seven CONNECTs
  observed). A preloaded shim (`NODE_OPTIONS=--require`, undici 8.10.1 ships
  in dsh's node_modules) works equally. The lane unit sets
  `NODE_USE_ENV_PROXY=1`.
- **Headless mode verified:** `dsh --profile headless --patch <overlay> "<task>"`
  prints the final answer on stdout and reasoning on stderr; exit 0 on
  success. Requests: `POST /v1/chat/completions`, `stream: true`,
  `stream_options.include_usage`, `store: false`, a ~33 KB system prompt
  with the tool catalogue, `User-Agent: deepseek-harness/0.1.2-rc.1`.
  A second small request generates a session title.
- **Config surface verified:** `--dump-default-config` (353 lines); the
  provider route is a `--patch` overlay on `llm-pi-ai.config.providers`
  plus `agent-default-model.config`; `DSH_PERMISSION_MODE`
  (`read-only|workspace-write|danger-full-access`; the last sets approval
  `never`), `DSH_TELEMETRY_MODE` (default `FEEDBACK_ONLY`, endpoint
  `harness-telemetry.deepseeksvc.com`; set `DISABLED`), `DSH_TOOLS_MODE`.
- **Second correction (same day):** the host pin's Node is 22.20.0, which
  does not implement `NODE_USE_ENV_PROXY` (tested: direct DNS attempt, no
  CONNECT); the 22.23 Node used for the earlier local test does. The lane
  therefore preloads `lib/proxy-shim.cjs` from the dsh package (undici
  8.10.1's `EnvHttpProxyAgent` as global dispatcher), verified on 22.20.0.
