# Concept 2026-09-22d — a concurrent writer during plan promotion duplicates content silently

**Class:** process defect, observed / harness-safety gap. **Status:** recorded 2026-09-22 from the `planning-patterns` ship run; no task types a fix yet.

**Origin (2026-09-22, promoting the `planning-patterns` draft):** the Ship phase's own instruction is "write this file to `docs/superpowers/plans/…` with the Write tool (typed headings append-only from then on)". The draft was 785KB (3,952 lines) — too large for one Read/Write round trip against the Read tool's 25k-token cap — so the promotion was done as one `Write` (the front matter) followed by a sequence of `Edit` appends, each anchored on the tail of the file as last written. Midway through, one `Edit` call returned success and the file's line count came back roughly 200 lines longer than either the source draft or anything this session had typed. Re-reading showed a `### PT6` heading appearing twice, each followed by a full, correctly-formed copy of the section — but the first copy was truncated mid-stream into a different section's tail before the second, complete copy resumed. A tool result on the very next `Edit` call also said, verbatim: "the file had been modified on disk since you last read it — the edit applied cleanly, but the file contains other changes not in your context." Diffing the target against the source draft found exactly one contiguous insertion (199 lines) with no other divergence anywhere in the 3,952-line file — i.e. something other than this session's own sequential edits had already written the *entire remainder* of the correct file, and this session's own next `Edit` landed on top of it rather than at the tail it still believed was current.

**Idea:** the guard that makes `docs/superpowers/plans/*.md` append-only through Edit/Write (`tools/orchestrator-guard.sh`) enforces *who* may write the file, but says nothing about *serializing* writers against each other — two writers each holding a stale read of the file (one appending by anchor-matching a remembered tail, one replacing the whole body) can interleave without either seeing a conflict, because Edit's anchor-match still succeeds against whatever text happens to be at that anchor in the *current* file, even if the file has grown past what the caller last read. The tool-level warning that surfaced here ("the file had been modified on disk... but contains other changes not in your context") is the only signal available, and it arrived *after* the collision had already happened, on the following call — nothing stopped the colliding `Edit` itself. A fix would need one of: (a) `Write`/`Edit` on a path under this guard's protection taking an optimistic-concurrency token (a content hash or mtime read at the start of the sequence) and refusing the whole append chain if the file moved underneath it, surfaced as a hard refusal rather than a post-hoc note; or (b) the promotion recipe itself never chunking a large plan file into sequential anchored appends — writing the whole body in one `Write` call regardless of size, so there is exactly one write and no window for a second writer to land in the middle of it.

**Payoff:** without either fix, any large-file promotion done through repeated Read-then-Edit-append is exposed to silent, structurally-valid-looking duplication whenever something else — another session, a background sync, a teammate — is also acting on the same path; the failure mode is not a refusal but a plausible-looking file that still parses (six `## ` headings, well-formed fences) while carrying a duplicated section, which is exactly the kind of defect a mechanical grammar checker (like this plan's own `patterns.py check`) would not catch unless it also asserted key/section uniqueness across the whole file, not just within one doc. The concrete recovery here was a full `diff` against the known-good source and a hand-repaired `Edit` that deleted the extra span — cheap only because an independent source of truth (the draft file) still existed to diff against; a promotion that discards its source after writing (or that has no byte-identical source, e.g. content authored inline) would have no such check.

**Dependencies:** `tools/orchestrator-guard.sh`'s plan-file rule (append-only via Edit/Write); whatever tool-call layer emits the "modified on disk" notice (its exact trigger and timing are themselves unmeasured — this concept only has the one observed instance); a future task would need to measure whether the notice is reliably emitted on every colliding write or only sometimes.

**Earliest landing:** not scheduled — surfaces again the next time a large plan or doc is promoted while another writer (session, sync process, or teammate) might also touch the same path; worth a session-start or promotion-runbook note before it recurs unnoticed on a file with no independent draft to diff against.
