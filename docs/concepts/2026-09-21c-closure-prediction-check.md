# Concept 2026-09-21c — a `touches`-to-closure check for plan `## Operator` sections

**Class:** planning-process defect, found by judging. **Status:** proposed (found during the operator-and-collection plan's judge panel, errata 8–9).

**Origin (judge panel, 2026-09-21):** judging `docs/superpowers/plans/2026-09-21-operator-and-collection.md`, the Opus judge re-checked the plan's own claim — `## Operator` step 4 and Assumption/A2 say "OC6–OC10 add nothing to the closure" and "no task touches `nixosModules/`, `hosts/` or `flake.nix`, but `pkgs/evidence` and `pkgs/broker` are inside two host packages" — against the tree and found it wrong on both counts: `nixosModules/seatLane.nix` builds `pkgs/seat` and `pkgs/dsh-openrouter` into the system closure (three lines: `seat-run`, `seat-submit`, the `dsh-openrouter` default), `nixosModules/helm.nix` builds `seat-submit` again, and `nixosModules/evidenceStore.nix` embeds the whole `pkgs/evidence` directory — so every task that touches `pkgs/seat`, `pkgs/dsh-openrouter` or `pkgs/evidence` changes the closure, not just the two the plan named. The same defect pattern shows up as errata 9: the plan scheduled its one `nixos-rebuild switch` after wave 2 on the strength of that same wrong claim, so OC9 (wave 3, rebuilds the seat unit) and OC10 (wave 4, rebuilds `evidence`) would land with no switch ever picking them up — the plan's own headline number (spend attribution reaching the broker) would stay at 0% forever under its own dispatch plan.

**Idea:** a plan's `touches` lists are already a complete, machine-readable set of every file every task will change. The set of host packages a change can reach is a fixed, small, and rarely-changing fact: `grep -rn 'callPackage ../pkgs/' nixosModules/*.nix` today shows exactly which `pkgs/*` directories are embedded in which system module (`seatLane.nix` → `pkgs/seat`, `pkgs/dsh-openrouter`; `helm.nix` → `pkgs/seat`; `evidenceStore.nix` → `pkgs/evidence`; the broker's own module → `pkgs/broker`). A small check — `nix develop -c python3 pkgs/evidence/tasks.py --root . closure-touch <plan.md>`, or even a five-line shell one-liner run at Ship time — could intersect a plan's unioned `touches` against that fixed package→module map and print which host packages the plan actually changes, catching exactly this class of error (the plan asserting "adds nothing to the closure" about a task that touches an embedded package) before it reaches a judge's manual re-derivation, and catching the second-order error (a switch scheduled before every closure-touching wave has landed) by comparing the touch set against the switch step's position in `## Dispatch`.

**Payoff:** this is the second time in recent plans (see the errata table) that a closure/touches mismatch has needed a judge to manually trace `nixosModules/*.nix` by hand against a plan's touched files — a mechanical check would catch it in the Ship-phase `check` pass alongside `waves`/`conflicts`, for the cost of one small, rarely-changing lookup table. It would also directly prevent the "switch scheduled too early" failure mode this plan's errata 9 found: a plan whose last closure-touching task lands after its only scheduled switch step is a plan whose own headline numbers cannot be measured.

**Dependencies:** none beyond `docs/ledger/subsystems.toml` (already read by `tasks.py`) and a new small lookup table over `nixosModules/*.nix`'s `callPackage ../pkgs/<name>` lines; no schema change, no plan-format change — the check reads `touches` and `## Operator`/`## Dispatch` step ordering, both already plain text in every plan.

**Earliest landing:** a task-zero addition to `pkgs/evidence/tasks.py`'s `check` subcommand ahead of or alongside the next plan whose `## Operator` section predicts a closure delta; until then, a Ship-phase judge should grep `nixosModules/*.nix` for `callPackage ../pkgs/<touched-package>` by hand for every plan that claims a bounded closure change.
