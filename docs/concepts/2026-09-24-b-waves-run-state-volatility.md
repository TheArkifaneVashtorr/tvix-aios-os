# Concept — `tasks.py waves` mixes a git-pinned graph with live, non-versioned run state

**Class:** process / tooling defect (planning-record hygiene)
**Status:** typed, not built — names a mechanism gap surfaced by measurement, not a design
**Origin:** the EV22r re-plan Ship phase (2026-09-24): the panel's judgement (`docs/reviews/plan-judgements/2026-09-24-ev22r.md`) carries four separate errata (1, 2, 7, 14) all rooted in one fact — `nix develop -c python3 pkgs/evidence/tasks.py --root . waves --repo nixos-agent-env --json`, re-run verbatim at the *same* HEAD `cc188189` that the plan cited, returned a different grouping (`FL5`/`FL6`/`FL7` present in the cited paste, absent on re-run) because `waves` derives group membership partly from each key's *derived* state (`ready`/`blocked`/`ran`/`running`), and derived state comes from `~/factory/runs` — a directory git does not track and a commit hash does not pin.

**Idea.** A plan file's "Waves" section is written once, at draft or Ship time, and then read by the operator and the seat as if it were as stable as the rest of the plan — sourced from the same HEAD, reproducible the same way every other cited fact is (per G11). But `waves`' output is a function of `(HEAD, wall-clock run state)`, not `HEAD` alone: dispatching a sibling key (a board commit like `15094fef`, recording `FL5` as dispatched) changes `waves`' answer without changing a single tracked file. So two runs of the identical command, at the identical git commit, minutes apart, can legitimately disagree — and every plan that quotes a `waves --json` grouping for a sibling plan's keys is quoting a value that is already stale by the time a judge or a seat re-runs it. This is not a bug in `waves` (the derived-state read is the point of the tool), but the *plans* that treat its output as a versioned fact, and the *panel rubric row* that treats a mismatch as an ordinary "wrong fact" MAJOR, both miss that this one command's output-class is structurally different from every other cited command's (`grep`, `wc`, a pytest run) — those are deterministic functions of the tree; this one is not a deterministic function of the tree.

**Payoff.** Naming the distinction lets three things happen without relitigating it plan by plan: (1) the judge rubric can carry a footnote — a `waves`/`conflicts` mismatch discovered on re-run is downgraded from "wrong fact" (which implies careless citation) to "stale run-state snapshot" (expected, cheap to fix) whenever the git-tracked half of the citation (the HEAD hash) still reproduces exactly; (2) a plan's own Waves section can be written to say so explicitly — "this table moves with run state, not only with HEAD" — rather than each re-plan rediscovering the same erratum shape (EV22r alone drew four rubric hits for one root cause); (3) `tasks.py waves --json` itself could optionally take a `--pin-run-state <file>` (a frozen copy of the relevant `~/factory/runs/*/*.result` status lines) so a plan's cited grouping is reproducible offline, the way `--files` already lets `subsystems.py validate` run against a frozen file list instead of the live tree.

**Dependencies.** `pkgs/evidence/tasks.py`'s `waves`/`conflicts` commands (the `scan_repo`/derived-state path, `tasks.py:1036-1043` and the state read from `~/factory/runs`); the judge rubric row 2 ("correct facts") in the batch-planning workflow; no code change is proposed here, only the naming of the gap — a fix (the rubric footnote, or a `--pin-run-state` flag) is a separate, later task.

**Earliest landing.** Whenever a Knowledge or Program task next touches the judge rubric text or `tasks.py`'s `waves`/`conflicts` CLI; no urgency, since the current workaround (re-derive at Ship time, note the volatility in the plan) already lands per re-plan without a mechanism change.
