# Concept — the five-step landing recipe has no single command; it is retyped by hand every wave

**Class:** process / tooling gap (orchestrator ergonomics)
**Status:** typed, not built — names a recurring cost surfaced by measurement, not a design
**Origin:** the 2026-09-24 error retrospective (`docs/research-2026-09-24-error-retrospective.md` §2 #12: "$18.03 of main-loop calls, no landing verb") and its implementation plan (`docs/superpowers/plans/2026-09-24-retro-fixes.md`, "Not in this plan": *"a landing verb for the orchestrator ... no §4 recommendation; parked in the concept file as a Factory increment (one command that runs recipe steps 1-4 with both exit codes gated)"*). The retro-fixes plan's own §Operator "Landing recipe per key" spells the same five steps out again, in prose, as the thing every one of its eighteen keys must be walked through by hand: reset the workspace to one commit, merge main forward if it moved, gate through `factory-review`, integrate and fast-forward, then dispatch what it unblocks — each a separate command, each gated on the previous one's exit code, typed fresh into a shell every time a key lands.

**Idea.** The recipe is already fully mechanical — every step names its exact command and its exact gating condition (`docs/superpowers/plans/2026-09-24-retro-fixes.md`'s "Landing recipe per key," steps 1-5), which is precisely what makes retyping it by hand wasteful and error-prone: a skipped merge-forward step, a `| tail` that masks the integrator's `CONFLICT` exit (the retro's own §2 finding, "never pipe the integrator"), or a wrong argument order are all failures of transcription, not of judgement. A `factory-land <run> <repo-path> <KEY>` verb would run steps 1-4 in order, stop and print the failing step's own output verbatim on any non-zero exit (never swallow it under `2>/dev/null`, matching the house rule), and on success run the same "what does this unblock" query Dispatch's step 5 already prints from `--dry-run`, so the orchestrator's only decision is whether to launch what comes back — the landing itself stops being an five-command improvisation and becomes one gated call, the same shape `factory-dispatch --dry-run` already gives the launch side.

**Payoff.** Three things follow from having the verb: (1) the retrospective's own root cause 3 ("driver and gates unsupervised") shrinks by one more surface — a landing's five steps currently run unsupervised in the orchestrator's own shell, exactly the class of failure ER12-ER16 close for the seat and the gate; (2) every future plan's §Operator section stops re-deriving the same five-step prose (this plan's own "Landing recipe per key" is the fourth time in two weeks these steps have been retyped, by the field-lessons ledger's own count of landing-run recipes since 2026-09-07); (3) the $18.03-per-wave main-loop cost the retrospective measured becomes a single command's worth of tokens instead of five hand-typed calls plus their outputs re-pasted into a chat turn.

**Dependencies.** `tools/factory/seat/factory-review`, `factory-integrate`, and the `git -C ... pull --ff-only` step the recipe currently spells out by hand; the retro-fixes plan's ER9/ER17 (judged-state and conflicts) are read-only inputs to "what does this unblock," not touched by this concept; no code change is proposed here, only the naming of the gap — the verb itself is a Factory-owned increment sized on its own merits (likely S: the four steps already exist as named commands, the new work is the sequencing, the exit-code gate and the one skipped-step message per stage).

**Earliest landing.** Whenever a Factory task next touches `tools/factory/seat/*` for an unrelated reason (e.g. the ER-series lands and a following wave needs the same seams), or on its own once two more waves have retyped the same recipe — whichever comes first; no urgency, since the current workaround (the plan's own written-out recipe, followed by hand) already lands every key without a mechanism change.
