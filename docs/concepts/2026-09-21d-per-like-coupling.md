# Concept 2026-09-21d — the per-like mutator unit still draws uncoupled from the carded pool

**Class:** deferred spec scope, parked at Ship. **Status:** proposed (named in the lora-cards-and-coupling plan's "Not in this plan" list, not yet speced).

**Origin (Ship phase, 2026-09-21):** `docs/superpowers/plans/2026-09-21-lora-cards-and-coupling.md` lands the coupled draw (`comfy-mutate --draw-stacks`, bound to the author's prompt through a shared stacks file, `requires` checked per variant, `trigger` prepended at enqueue) only for the supervisor's authored-prompt path (`comfy-run-<w>.service`: draw → author → mutate). The world still runs a second, independent LoRA consumer — the per-like mutator unit `comfy-mutate-<w>.service` — that draws its own stack from the carded pool on every liked render, with no author in that loop to tell and no prompt written for the draw to match. The plan's own spec-to-task map names this explicitly: "the per-like mutator unit `comfy-mutate-<w>.service` keeps drawing uncoupled from the carded pool (no author to tell — its coupling is a later spec)". After this plan lands, the per-like path will draw from the now-carded, now-typed pool (`category`, `trigger`, `requires` all populated by `comfy-cards` and the operator's adjudication) but still ignore every one of those fields the same way the pre-this-plan world ignored everything — the coupling mechanism this plan builds (draw-first, bind, check `requires`, prepend `trigger`) has no analogue on that unit.

**Idea:** the per-like unit has a structural difference from the supervisor path that any future spec has to resolve before it can reuse GN50/GN51's draw-then-bind shape: there is no author call to hand a stacks file to, and the source text (a liked render's own past prompt, replayed with a swap) is not written *for* the drawn stack the way an authored prompt is. Two shapes are available and worth stating side by side rather than rediscovering at spec time: (a) draw the stack, then filter the mutation's swap space to candidates whose surviving text still satisfies `requires` for that stack (a `requires`-aware swap rather than a `requires`-aware author), dropping the stack when nothing survives — this reuses `_word_in` and the drop/count contract GN50 already ships, just applied after the swap instead of after authoring; or (b) leave the per-like path uncoupled by design (its LoRA is exploratory, discovered by the swap/mutation search rather than declared by category) and instead spend its `trigger`/`requires` fields only as a *scoring* signal for `lora_stack_weights` (a member whose `requires` the surviving text already satisfies gets upweighted), never as a hard gate. (b) needs no new CLI surface and is the smaller change; (a) gets full parity with the supervisor's coupling contract at the cost of a second binder.

**Payoff:** without a decision here, the world that ships this plan still exhibits — on its per-like path only — exactly the "a LoRA that fires whether or not the prompt asks for it" symptom the spec (`2026-09-21-lora-cards-and-coupling-design.md` §1) was written against, just narrowed from every render to the subset seeded by likes. The operator's adjudication work in this plan's Operator step 5 (about 35 rows carded with `category`/`trigger`/`requires`) is fully reusable by whichever shape lands — the card grammar and pool rule (GN47) do not change — so this is scoping work for a follow-on spec, not lost effort now.

**Dependencies:** the carded pool and validators from this plan (GN47: `CARD_CATEGORIES`, `_card_word_ok`, the pool rule) and the token-boundary rule `_word_in` (GN50 Interfaces 3); no new manifest keys either shape needs beyond what this plan already lands.

**Earliest landing:** a spec, after this plan's Operator steps 1–7 have run on the live worlds long enough to show whether the per-like path's un-coupled draws are visibly a problem in practice (the search-loop spec's judge, `2026-09-21-search-loop-design.md`, may also want a say in whether liked renders should be require-gated at all) — not a task inside this plan.
