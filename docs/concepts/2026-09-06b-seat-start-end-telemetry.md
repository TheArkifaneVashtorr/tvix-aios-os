# Concept 2026-09-06b — factory-wave records shape-B start/end rows

**Class:** telemetry / process. **Status:** parked (named in the telemetry-store sub-project 1 plan's "Not in this plan" section; not designed). **Origin:** the telemetry-store design's `factory-run` kind declares two shapes — A (the dark-factory recorder's end-of-run report) and B (`driver: "seat"`, `event: start|end`) — but sub-project 1 lands only the fence that accepts shape B and the `.result`/`.review.md` ingests; nothing yet calls `evidence.append("runs", …)` with a shape-B row from the seat driver itself.

**Idea.** `tools/factory/seat/factory-wave` is the one place that knows a wave's full task list, its base commit and its process id before any task starts, and knows every task's terminal status when the wave's children exit. Two `append` calls — one at the top with `event: "start"`, `run_id`, `plan`, `base`, `groups` (the peeled-off wave list), `pid`; one at the bottom with `event: "end"`, the same `run_id`, and `tasks: [{key, status, commit, fix_rounds}, …]` built from what `factory-integrate`/the landing recipe already observed — would give the join a run-level frame around the per-task `derived/tasks` rows T2's `ingest result` already produces per task. Today a run's shape is reconstructible only by grepping `~/factory/runs/<run>/*.result` file mtimes and the board's queue-block history; a shape-B pair makes "how long did wave 2 take, and which of its three tasks were still running when the wave was killed" a `join_tasks_gates`-style query instead of a manual reconstruction.

**Payoff.** T10b's ladder report (parked, not in this sub-project either) wants a run's wall-clock envelope and its declared task set to compute readiness and detect an abandoned wave (a `start` row with no matching `end`); without shape-B rows that envelope does not exist in the store at all. The relaunch table (A6 in this plan) also wants to know a dead seat's declared `groups` without opening its log. Landing this early is small: T2 already gives `factory-wave` the ingest CLI and the `EVIDENCE_STORE`/`FACTORY_EVIDENCE_CMD` plumbing it needs; the two `append` calls are the only new code.

**Dependencies.** T1 (the fence, `factory-run` shape B, `evidence.append`) must land first — the shape is already declared in T1's `KINDS` table, so no schema change is needed, only the two call sites. Reads best after T10a's `join_tasks_gates` exists, though it does not depend on it to land.

**Earliest landing.** XS once T1 lands (named as T16 in the parent design's numbering); does not block or get blocked by any task in this sub-project's plan.
