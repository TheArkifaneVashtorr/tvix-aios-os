# Concept — the IS23 re-plan (IS23r/IS28/IS29): judged and dispatch-checked, plan file not shipped

**Class:** process / tooling limitation
**Status:** typed, not built — records a Ship-phase blocker, not a design
**Origin:** the 2026-09-24 IS23 re-plan workflow (dispatch decision on the panel scores in `docs/reviews/plan-judgements/2026-09-24-is23r.md`); the harness's sandbox for this session forbade `sudo`, any non-dry-run `factory-dispatch`, and any Bash write to `docs/superpowers/plans/*` (the orchestrator guard's append-only-headings rule, `tools/orchestrator-guard.sh`'s `HEADING_REASON`), leaving `Write`/`Edit` as the only route to the plan file.

**Idea.** The Ship phase asked for four things: (1) write the judgement file, (2) verify every existing `### ` heading of `docs/superpowers/plans/2026-09-11-isolation.md` survives byte-identical in the draft and then write the draft whole over the plan, (3) run `tasks.py check`/`conflicts`/`waves --next` and a dry-run `factory-dispatch`, (4) write this concept. Item 1 is done: `docs/reviews/plan-judgements/2026-09-24-is23r.md` carries the front matter (scores, total 36, threshold 34, decision dispatch), the 21-row errata table, and all three judges' reasons.

Item 2's heading check itself passed cleanly: `comm -23 <(grep '^### ' <plan file> | sort -u) <(grep '^### ' <draft> | sort -u)` printed nothing — every heading in the live plan (IS10 through IS27, including every lettered fix round) is present byte-identical in the draft. But the orchestrator guard's own append-only check on `Write`/`Edit` calls against the plan file is stricter than that comparison: it refuses a write whose *resulting* file is missing any of the live file's `### ` headings at that instant, and — because `Write` replaces the whole file in one call — every intermediate call in this session that did not yet carry the full ~2,400-line draft (all 29 task sections, IS10 through IS27) tripped the same refusal, even though the *final* intended content was correct. The draft is roughly 330 KB / 2,386 lines; reproducing it verbatim in a single `Write` call, byte for byte, inside one model turn repeatedly ran into the turn's own output-size ceiling before the call could complete, and a partial write is exactly the state the guard is designed to reject.

**Payoff.** Naming this now, rather than silently leaving the plan unshipped, gives the next session (or the operator) three concrete options instead of a rediscovery: (a) ship the draft through a tool path that accepts a file argument rather than inline content — an editor `open_in_editor` / host-side copy the operator runs by hand, or a future harness capability that lets `Write` take a source path instead of literal text; (b) raise the per-call output budget or ask the harness to permit a `Write` follow-up mode that appends to a file it already staged, so the heading check runs once against the complete result rather than per partial call; (c) accept a human-in-the-loop step: the operator runs `cp` themselves (outside the sandbox's Bash-tool restriction, which binds the agent, not the operator) after reviewing the diff, since the draft's own byte-identical-heading property is already proven by the `comm` check above and needs no further agent action.

**Dependencies.** `docs/reviews/plan-judgements/2026-09-24-is23r.md` (written); the draft `draft-0.md` in this session's scratchpad (unpublished, would need re-creating in a future session since scratchpads are session-scoped); the live `docs/superpowers/plans/2026-09-11-isolation.md`, unchanged at 231,327 bytes, still carrying the un-replanned IS23 heading rather than IS23r/IS28/IS29.

**Earliest landing.** The next session with either a larger single-turn output allowance for the `Write` tool, or an operator-run copy step reviewed against this session's `comm -23` proof and the judgement file's errata table.
